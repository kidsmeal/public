## Summary
This builds Gantry's two phase-enforcement PreToolUse hooks (a file-list guard on `Edit|Write|MultiEdit` and a commit guard on `Bash`), backed by a sentinel file written and cleared by a dedicated `sentinel.js`, all sharing one read+path-normalization helper so the read and write sides cannot drift. It ships in five dependency-ordered phases: the shared helper first, then the sentinel writer, then the two guards, then plugin-native hook registration plus the `init.js` opt-in, then the orchestrator doc wiring (build.md / review.md / SKILL.md) and README. Every code phase is proven by a `node --test` file in the existing style.

## Phase 1: Shared sentinel-read + path-normalization helper
**Goal:** Build the one module that reads the sentinel and decides whether a given `file_path` is in-scope, so the read side (guards) and write side (sentinel.js) share identical path logic and cannot drift.
**Files:**
- create `plugins/gantry/scripts/sentinel-core.js` (exact name at implementer's discretion; the design calls it "a shared helper for sentinel read + path normalization"). Exports at minimum: read the active sentinel (path resolution + JSON parse, returns null on absent/malformed), a staleness check (session-mismatch AND `started` older than the 6h threshold), project-root resolution matching `init.js`'s `ROOT` order, and a `normalize(file_path)` that lowercases the drive letter, converts `\` to `/`, and relativizes against the project root - returning a sentinel value (not a throw) when the target escapes the root or no root resolves, so callers fail OPEN.
- create `test/sentinel-core.test.js`
**Verification:** `node --test` from repo root, with `test/sentinel-core.test.js` covering, at minimum, every path case in the design's Edge cases: Windows absolute backslash path vs repo-relative POSIX `files` entry (match), drive-letter case difference (match), forward-slash absolute path (match), a path genuinely outside the list (no match), a target that escapes the project root (returns the fail-open signal, not a deny), missing/empty `file_path` (fail-open signal), absent sentinel (null), malformed sentinel JSON (null, no throw), stale-by-session and stale-by-age (treated inactive), fresh-and-matching-session (active). Use `GANTRY_PROJECT_DIR` to pin the root like `init.test.js` does.
**Exit criteria:** The helper has zero dependencies, `"use strict"`, a top-of-file block comment; all new tests pass under `node --test`; no normalization branch throws (every error path returns a value the caller reads as fail-open); the full existing suite still passes.
**Blockers:** None. The 6h staleness threshold and the exact stale rule (session mismatch AND age) are decided in the design.

## Phase 2: sentinel.js writer (write / clear / add-files)
**Goal:** Build the dedicated script that writes, clears, and appends to `.gantry/active-phase.json`, computing the file-list and allow-list from a plan + phase so the orchestrator never touches the sentinel via a tool op.
**Files:**
- create `plugins/gantry/scripts/sentinel.js` with subcommands `write <plan> <phase>`, `clear`, `add-files <path>...`. It reads the phase's Files list from the plan file, computes `allow` (the plan path plus the two scaffolded audit doc paths resolved with the same `docs/`-vs-root logic as `init.js`'s `docDir`, plus `ROADMAP.md` only if that file actually exists), stamps `started` (ISO) and `session` (from its argument or env, see below), and writes the sentinel via `fs`. `add-files` appends reviewer-cited paths to the active sentinel's `files` idempotently. It reuses Phase 1's helper for read + path normalization so write-side and read-side paths match.
- create `test/sentinel.test.js`
**Verification:** `node --test` from repo root, with `test/sentinel.test.js` covering: `write` produces a sentinel whose `files` equals the plan phase's Files list and whose `allow` resolves the audit docs to `docs/` when a `docs/` dir exists and to root when it does not (mirror `init.test.js`'s two-mode scaffolding tests); `write` includes `ROADMAP.md` in `allow` only when the file exists; `clear` removes the sentinel and is a no-op when none exists (no throw); `add-files` appends without duplicating an already-listed path and is a no-op against an absent sentinel; a second `write` overwrites a prior sentinel (single-writer property). Pin the project dir with `GANTRY_PROJECT_DIR`.
**Exit criteria:** All new tests pass; the script writes the sentinel only through `fs` (never via the Edit/Write tools - it is a node script invoked over Bash); house style satisfied; existing suite still green.
**Blockers:** **Plan-parsing contract for the Files list.** The design says sentinel.js "reads the phase's file list from the plan." This plan's own `## Phase N` / `**Files:**` format is the de facto shape, but the parser's exact extraction rule (which lines under `**Files:**` become `files` entries, how `create`/`modify` prose and backtick-wrapped paths are stripped to bare repo-relative paths) is not pinned in the design. If, when implementing, the extraction rule is ambiguous enough that a reasonable plan would parse wrong, stop and report it rather than inventing a fragile regex - this is the one place the writer can silently disagree with the human's plan. (Listed as a phase-internal caution, not a top-level blocker, because the plan format is observable from this very file; surface it only if the format proves underspecified in practice.)

## Phase 3: The two PreToolUse guards (file-list-guard, commit-guard)
**Goal:** Build the two hook scripts that read stdin, consult Phase 1's helper, and either allow (exit 0) or emit the deny JSON - failing OPEN on every error.
**Files:**
- create `plugins/gantry/scripts/hooks/file-list-guard.js` (matcher `Edit|Write|MultiEdit`): exit 0 if no `.gantry/enabled` marker; exit 0 if no active (non-stale) sentinel; else normalize `tool_input.file_path` and each `files`/`allow` entry via the shared helper; exit 0 if in either list; else print the deny JSON with the scope-drift message. Missing `file_path` -> fail open (exit 0) with a logged note.
- create `plugins/gantry/scripts/hooks/commit-guard.js` (matcher `Bash`): same opt-in + active checks; then scan `tool_input.command` for `git commit`/`git push` as a command head at any point a new command can start (`^`, `&&`, `;`, `|`, `(`), allowing flags and a leading `-C <path>`, NOT matching the substring inside a quoted argument; on match print the deny JSON; else exit 0.
- create `test/file-list-guard.test.js`
- create `test/commit-guard.test.js`
**Verification:** `node --test` from repo root. `test/file-list-guard.test.js`: feed the guard a stdin payload (write a fixture sentinel + `.gantry/enabled` under a temp `GANTRY_PROJECT_DIR`, pipe JSON via `spawnSync`'s `input` option) and assert exit 0 + empty stdout for an in-`files` path, an in-`allow` path, no-marker, and no-sentinel; assert the deny JSON (`hookSpecificOutput.permissionDecision === "deny"`) for an out-of-list path; assert fail-open exit 0 for missing `file_path`, malformed sentinel, and unresolvable root. `test/commit-guard.test.js`: assert deny for `git commit -m x`, `git push`, `foo && git commit ...`, `x; git push`, `( git commit )`, and `git -C ./sub commit`; assert allow (exit 0) for `echo "how to git commit"`, `git status`, `git log`, and the plumbing call `node .../sentinel.js write ...`. Both: assert exit code is always 0 even when denying (deny is via stdout JSON, not a non-zero exit).
**Exit criteria:** Every guard test passes; both guards exit 0 on every error path (no unhandled throw can produce a non-zero exit); the deny JSON matches the design's block contract exactly (`hookEventName: "PreToolUse"`, `permissionDecision: "deny"`, `permissionDecisionReason`); commit-guard never denies a `node sentinel.js` Bash call; existing suite green.
**Blockers:** Stdin field-name confirmation (see top-level Blockers, verify against current docs while writing the parser). Deny-message final wording is an explicit tuning pass here, not a design gate (design Open questions).

## Cross-cutting concerns

- **New always-loaded plugin hooks (`plugins/gantry/hooks/hooks.json`).** What changes: every Gantry plugin install begins loading two PreToolUse hooks on `Edit|Write|MultiEdit` and `Bash` for all sessions, including subagent tool calls. What it affects: every tool call in every session of every installed copy. Ordering: lands in Phase 4, but is **inert** until Phase 1-3 scripts exist AND a project writes `.gantry/enabled` AND an active non-stale sentinel exists - so Phases 1-3 must merge before 4 makes the hooks reachable, and even then nothing is enforced until opt-in. Compatibility/rollback: installing the update changes nothing for any existing user until they run `/gantry:init` and opt in; a manual `.claude/` copy never loads `hooks.json` at all (no plugin), preserving "manual copy works without the hooks." Rollback is deleting `.gantry/enabled` (inert again) or the `hooks.json` (gone). This is the single highest-blast-radius change in the feature and is why every guard must fail OPEN.

- **Fail-open is a hard invariant spanning Phases 1 and 3.** What changes: the guards must exit 0 (allow) on ANY error - malformed sentinel, unreadable marker, missing `file_path`, unresolvable project root, or a target path that escapes the root. What it affects: the entire repo's editability; a fail-CLOSED bug bricks edits for every opted-in project. Ordering: the helper (Phase 1) must return fail-open signals rather than throw, and the guards (Phase 3) must treat those signals and every catch as exit 0. Note: the design explicitly flags the "wrong-but-valid root relativizes to a non-matching path" case as a fail-CLOSED trap that must be coded as fail-OPEN. Tests in both phases must assert exit 0 on every error path. No rollback needed if respected; if violated it is a P0 brick.

- **Orchestrator control-flow contract change (build.md / review.md / SKILL.md).** What changes: three doc files that drive the implementer/reviewer loop gain sentinel write/clear/add-files steps; the implementer is now gated mid-phase by a hook, where before it was prompt-only. What it affects: the live behavior of `/gantry:build`, `/gantry:review`, and `/gantry:run`. Ordering: Phase 5, and the write/clear/add-files calls must sit at the exact points fixed by the design (write before the implementer spawn; clear at ready-to-commit; add-files before a fix re-spawn). Migration: these are additive doc instructions, no data migration. Rollback: revert the three files; the scripts then exist but are never invoked, so the sentinel is never written and every guard no-ops (inert), which is safe.

- **The sentinel must never be written or removed via a tool op (spans Phases 2, 3, 5).** What changes: all sentinel mutation goes through `node sentinel.js` over Bash; no agent issues a raw `Write` or `rm` against `.gantry/active-phase.json`. What it affects: the deadlock-avoidance property - the file-list guard ignores Bash, and the commit-guard only denies `git commit`/`git push`, so a `node sentinel.js` call passes both. Ordering: the commit-guard's matcher (Phase 3) must be confirmed to NOT match `node ... sentinel.js`, and the orchestrator wiring (Phase 5) must use only `node sentinel.js` (verified by re-reading the edited docs). Rollback: n/a; this is an invariant the tests in Phase 3 (commit-guard allows `node sentinel.js`) and the Phase 5 re-read both enforce.

- **`.gitignore` creation and the `.gantry/` directory contract (Phase 4).** What changes: a repo-root `.gitignore` is created where none exists; `.gantry/active-phase.json` is ignored (transient run state) while `.gantry/enabled` is committed (shared team opt-in). What it affects: what Git tracks in every opted-in project. Ordering: Phase 4, gated on `CLAUDE_PLUGIN_ROOT`. Migration: additive and idempotent - never duplicate the ignore line, never overwrite an existing `.gitignore`. Rollback: remove the appended line; the marker file is harmless if committed. Note: this Gantry repo itself has no `.gitignore` today, so dogfooding init here would create the first one.

- **Shared helper is a single point of drift control (Phase 1, consumed by 2 and 3).** What changes: one module owns sentinel read + path normalization for both the writer and both guards. What it affects: if the read side and write side ever computed paths differently, the guard would deny edits the writer authorized (or vice versa). Ordering: Phase 1 must land and be fully tested before Phases 2 and 3 build on it; it is the reason this is phase 1 and not folded into the guards. Rollback: n/a; it is the foundation, not a swappable layer.

- **No schema, no network, no new runtime dependency.** Explicitly called out by the design so the implementer does not add one. The sentinel JSON is internal transient state, not a versioned on-disk schema with migration obligations; a malformed or future-shaped sentinel is handled by fail-open, not by a migration.
