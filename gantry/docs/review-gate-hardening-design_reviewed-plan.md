## Summary
This hardens Gantry's review gate in two independently-shippable blocks. **v1 (Phases 1-3)** is prompt/doc-only: a planner-declared wiring line (U1), reachability + real-input checks on the phase-reviewer with its Hard-rule command exception (U1, U2), the implementer's real-input verification rule (U2), reviewer FAIL scope calibration (U3), and the orchestrator's informed-escalation round cap that keeps the existing 2-cycle stop unchanged (U3) - each proven by section-presence assertions added to `test/consistency.test.js` (U5). **v1.5 (Phases 4-6)** is the cross-model adversary (U4): the additive `adversary` resolution on `role-core.js`, the `role.js` `resolve`/`run --adversary`/`show` surfaces, the `models.json` schema doc, and the orchestrator adversary final-pass + fix-relay step - proven by new `test/role-core.test.js` and `test/role.test.js` cases plus the consistency check on `models.md`. The phase order makes the entire v1 block land and pass before any v1.5 routing code, so v1 can be paused and measured before v1.5 is built (the design chose to build both, but the ordering preserves the measurement boundary).

## v1 vs v1.5 split
- **v1 (cheap gap-closers, prompt/doc-only, no routing code, no recurring cost):** Phase 1, Phase 2, Phase 3. After Phase 3 the suite is green and v1 is a complete, shippable block. This is the pause/measure point.
- **v1.5 (the cross-model adversary, routing code + config schema + recurring external-model cost):** Phase 4, Phase 5, Phase 6. None of these fire on a project with no `adversary` configured; default behavior is byte-for-byte today's.

## Cross-cutting concerns

- **`.gantry/models.json` schema change (additive `adversary` field) - U4, Phases 4-6.** What changes: a reviewer role assignment gains an optional `adversary` object shaped like a role assignment (`{ backend, model }`). What it affects: the config every project reads through `loadConfig` -> `parseConfig` -> `resolveRole`, and what `/gantry:models` (`show`) prints. Ordering: the parser/resolver tolerance lands in Phase 4 (`role-core.js` fails safe to no-adversary on any malformed entry), the surfaces in Phase 5, the doc in Phase 6. Migration/rollback: no schema-version field exists and none is added; the config is parsed leniently, so every existing `models.json` (including this repo's, which has a codex `phase-reviewer` and no adversary) keeps resolving to single-reviewer behavior unchanged. `DEFAULT_CONFIG` is untouched. Rollback is removing the `adversary` key (back to single reviewer) or reverting the three v1.5 phases (the routing code goes away; a stray `adversary` key in a config is then simply ignored by the old parser). This is the only schema-touching change and it is forward- and backward-compatible by construction.

- **Public contract: `resolveRole`'s return shape (additive) - U4, Phase 4.** What changes: `resolveRole` gains an optional `adversary` descriptor on its return object, only on the two reviewer roles when a valid adversary is configured. What it affects: every caller of `resolveRole` - `role.js` (`cmdResolve`, `cmdRun`, `cmdShow`) and the `test/role-core.test.js` suite. Ordering: Phase 4 adds the field; Phase 5 is the first consumer. Migration/rollback: all existing return fields (`role`, `error`, `dispatch`, `type`, `backendName`, `model`, `backend`, `harnessGuard`) are unchanged, so every existing caller and every existing `role-core.test.js` case keeps passing without edit (the design requires this and the plan's Phase 4 verification asserts it). The implementer harness lock (`HARNESS_SAFE_TYPES`) is unaffected and never applies to a reviewer's adversary. Rollback: drop the field; old callers never read it.

- **Orchestrator control-flow contract (SKILL.md / run.md / review.md / build.md) - U3 (Phase 3) and U4 (Phase 6).** What changes: the per-phase loop prose gains (Phase 3) an informed-escalation read at the existing 2-cycle cap and (Phase 6) an adversary final-pass step with its own fix relay and cap. What it affects: the live behavior of `/gantry:run`, `/gantry:review`, `/gantry:build`. Ordering: the round-cap edit (Phase 3) is v1 and must land before the adversary step (Phase 6) so the adversary's "under its own round cap" reuses the same informed-escalation rule; `build.md` is part of the Phase 6 loop but gains no new logic (it re-spawns the implementer as today, the existing FAIL fix path). Migration/rollback: additive doc instructions, no data migration; with no adversary configured the Phase 6 step never fires, so the pipeline is byte-for-byte today's. The round-cap edit (Phase 3) keeps the 2-cycle value and unit unchanged - it sharpens the existing stop, it does not retune it. Rollback: revert the prose; the routing code then exists but is never invoked by the loop (a `resolve` still prints `ADVERSARY:` but nothing acts on it).

- **Round-cap value is a published-tool value - do NOT silently retune (U3, Phase 3).** What changes: nothing about the number. The existing 2 fix cycles stay; only the escalation message gains the trajectory read + three options. What it affects: the user-facing behavior of a shipped tool. Ordering: Phase 3. Migration: the design explicitly drops the grill's "N=3" because silently re-tuning a shipped value is out of scope; the Phase 3 verification asserts the "2"/"cycles" literals survive, guarding against an accidental bump. Rollback: n/a (no value changed).

- **Reviewer Hard-rule command budget exception (U2, Phase 1).** What changes: the phase-reviewer's Hard rule currently caps it at running only the plan's named verification command once with "No ad-hoc scripts." Phase 1 adds the real-input smoke run as an explicit new allowed command. What it affects: the reviewer's own contract - without this exception the reviewer is forbidden from doing the U2 check the same unit requires. Ordering: must land in the same edit as the U2 real-input reviewer check (Phase 1), or the contract self-contradicts. Migration/rollback: prose-only; rollback removes both the check and the exception together.

- **No schema migration, no network, no new runtime dependency, no change to the implementer's harness lock or the file-list/commit hooks.** Explicitly called out by the design so the implementer does not add one. The `adversary` config is internal, leniently parsed, not a versioned on-disk schema with migration obligations; a malformed or future-shaped adversary entry is handled by fail-safe-to-no-adversary, not by a migration. The implementer harness lock (`HARNESS_SAFE_TYPES`) and the phase-enforcement hooks (file-list guard, commit guard) are untouched.

- **Build-ordering invariant (the measurement boundary).** What changes: nothing in code; this is a phase-ordering constraint. The entire v1 block (Phases 1-3) must land and pass `node --test` as a coherent, independently-shippable unit before any v1.5 routing code (Phases 4-6). What it affects: the ability to pause and measure whether the single primary reviewer alone closes findings 1-3 before paying for the cross-model adversary. Ordering: Phases 1-3 first, in that order (reviewer hardening, then planner+implementer, then the orchestrator cap that v1.5's adversary cap reuses); then Phases 4-6 (core resolution, then dispatch surfaces, then orchestrator wiring + doc), in that order (each depends on the prior). The design chose to build both v1 and v1.5 together, knowingly forgoing the "did the primary alone suffice" measurement; this ordering preserves the option to stop after Phase 3 if the user decides to measure.
